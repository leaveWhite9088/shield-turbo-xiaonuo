## 一、核心定位：为什么把“性能优化”与“安全加固”绑在一起考？

在真实的后端与系统工程中，**极限性能（Turbo）**与**铜墙铁壁的安全（Shield）**天然是一对**“互斥紧箍咒（跷跷板）”**：
* 如果模型为了刷高吞吐量和低延迟，无脑上全局内存缓存、删掉鉴权校验或拆掉事务锁，就会立刻导致**跨租户机密数据串味泄密或并发越权穿盾**（安全分崩盘）；
* 如果模型为了堵死并发漏洞和恶意输入，无脑在入口套一把全局线程死锁、在循环里查十遍权限或写极慢的嵌套正则扫描，又会立刻把**并发吞吐量和响应延迟拖垮**（性能分崩盘）。

### 核心任务形态
开局给所有被测模型同一个**“业务逻辑 100% 正确、自带功能测试全绿，但既慢（暗藏多级性能黑洞）又脆（暗藏多级安全漏洞与拒绝服务攻击面）”**的中大型 Python 在线业务系统（例如：多租户实时风控决策与企业级合规文档检索网关，仅依赖 Python 标准库与本地 SQLite，零外部服务依赖）。

选手的唯一使命是：在**确保所有正常业务请求的计算结果与原版分毫不差（哪怕改错一个业务数值都会触发毁灭性封顶归零）**的前提下，对系统进行深度重构优化与安全加固，使其在一键出榜时顶住**“大规模高压性能压测机”**与**“红队黑客实弹攻击机”**的双重轰炸。

## 二、吸取前序实测教训：五大“反高分通胀”硬性设计铁律

前序排障与后端 v1.0 实测表明：如果给选手配了能反馈对错的预发门禁、如果代码里的错误写得像教科书一样直白、如果用“一把全局大锁”就能逃掉并发课、或者采用“改对即满分”的静态计分，模型就会全部挤在 90 分以上。**因此，构建本基准时必须严格落实以下五条铁律：**

1. **铁律一：严禁提供任何“预发验题机”、红队攻击脚本或性能打分回显！**
   * 沙盒内公开给选手的自检脚本（`smoke_check`）**只允许运行小规模的正常业务功能回归测试**（帮选手确认自己没有把基本业务接口改崩）。
   * **绝对禁止**在选手阶段暴露出榜时使用的大规模高压数据集、红队黑客攻击载荷（Exploit Payloads），也**绝对禁止**在选手沙盒脚本里回显“当前提速多少倍、拿了多少分、还有哪几个安全漏洞没堵上”！所有高压压测与红队实弹攻防只在一键出榜（`finalize.py`）时执行。
2. **铁律二：严禁写出“头顶挂着标准答案注释、脚下写着十行直白笔误”的教科书代码！**
   * 沙盒里的初始系统必须具备真实商业项目的模块纵深与代码体量。性能瓶颈与安全漏洞必须自然地融合在跨模块的正常业务逻辑流转中。
   * **代码注释彻底去剧透化**：注释只准描述正常的商业背景与接口用途，**严禁**出现诸如“注意：此处暂未加索引”、“TODO：可能存在并发越权或正则回溯”等任何泄漏病灶位置的提示语！
3. **铁律三：A 层性能分采用“连续对数加速比曲线”，像《硅基骑手》算净利一样取消静态满分天花板！**
   * 绝不按“有没有改某行代码”给分，而是直接拿实测物理秒数、查询次数与内存峰值说话：在一键出榜的大规模压测下，计算选手相对初始原版的**真实加速倍数（Speedup Ratio = 原版基准耗时 / 选手实测耗时）**、**I/O 查询削减率**与**内存下降率**，按对数插值曲线连续算分。
   * 只改表层 SQL 或加个普通索引（提速 2～3 倍）只能拿到 10～13 分（及格线以下）；必须把平方级算法降维成线性/哈希算法、做好批量流式处理与高命中率隔离缓存（提速 25～50 倍以上），才能逼近 30 分满分。
4. **铁律四：“性能—安全跷跷板互锁” + “一把大锁惩罚” + “改坏业务直接封顶归零”！**
   * **狙击“一把全局大锁逃并发课”**：在 A 层性能压测中必须包含**高并发读写混合压测**！如果选手为了应付 C2 并发安全测试而偷懒加了一把全局线程锁或全库粗暴串行锁，虽然能防住超扣，但高并发读写的吞吐延迟会严重退化，导致 A 层并发吞吐分大幅扣减！
   * **狙击“无脑全局缓存泄密”**：热点检索与策略计算不加缓存拿不满性能分；但如果选手偷懒用了不区分租户上下文的全局缓存、或者在租户权限变更/数据撤回时未做精准缓存失效，C1 红队测试会紧接着发起“权限收回后跨租户缓存刺探”，一旦读到脏缓存直接判定为严重泄密事故重扣安全分！
   * **狙击“删业务代码骗取假高速”**：如果选手为了刷出 0.1 毫秒延迟而删掉正常计算逻辑或返回残缺结果，**一旦 B1 业务无损对账准确率低于 100%，A 层性能分与 B2 时间分必须乘以 `(B1_accuracy) ** 4` 强力封顶（业务算错即性能与速度分归零）**！
5. **铁律五：收紧 B2 时间衰减 + 盲评强制绑定“官方 5 级平庸参照补丁”**
   * 端到端耗时 `8` 分钟内满分 `10` 分，超出后按 `10` 分钟半衰期陡峭衰减；
   * 盲评包内强制附带《官方 5 级平庸参照补丁样本》（特征：只加了表层索引、套了粗暴全局锁、用脆弱的字符串黑名单替换应付安全检查）。评委规则写死：**凡是优化与加固的工程思想未明显超越该 5 级平庸样本的，D 层单项最高锁死在 5 级（即 D 总分 ≤ 15/30）！**

## 三、性能黑洞与安全漏洞的“浅、中、深”三段位矩阵设计

请在初始沙盒系统中精心织入以下三个段位的性能瓶颈与安全攻击面，确保弱模型、中等模型与顶尖模型停留在截然不同的分数梯队：

### 1. 性能压榨三段位（支撑 A 层 30 分连续加速曲线）
* **第一段位（表层 I/O 与连接开销，提速 2～4 倍可达）**：
  * 典型跨表高频查询缺失核心复合索引；
  * 列表组装与权限聚合中存在隐蔽的跨模块循环内查库（N+1 查询放大）；
  * 高频路径中重复打开/关闭连接或对大体积静态规则配置进行逐请求重复解析反序列化。
* **第二段位（算法复杂度降维与内存流式化，提速 8～15 倍可达）**：
  * 核心检索匹配、相似度去重或滑动时间窗风控聚合中，藏有 $O(N^2)$ 嵌套遍历或多次全表拉入 Python 内存做笛卡尔比对（在小样本冒烟时仅需 10 毫秒毫无察觉，出榜灌入上万条高压数据时耗时飙升至十余秒、内存暴涨数倍，必须改写为倒排/哈希索引、单次扫描预聚合或 SQL 窗口/批量算子）；
  * 报表与大批量数据导出时全量加载进内存列表拼接，需优化为游标流式生成以降伏峰值内存。
* **第三段位（高并发读写分离、细粒度锁与租户隔离缓存，提速 25～50 倍可达）**：
  * 针对高频热点规则树评估与租户权限拓扑计算，需设计**租户隔离 + 版本/事件驱动精准失效**的内存缓存机制，并配合 SQLite WAL 读写并发优化与细粒度键级锁（按租户或资源 ID 分片加锁而非全局一把锁），在保证绝对安全与一致的前提下把高并发 P95/P99 延迟压到极限。

### 2. 红队安全攻防三段位（支撑 C 层 25 分实弹轰炸）
* **第一段位（注入、路径穿越与敏感脱敏，C1 基础）**：
  * 动态排序字段、自定义过滤表达式或批量拼接中的隐蔽 SQL 注入攻击面；
  * 审计快照/文档导出接口中，可被双重编码、反斜杠或相对路径绕过的目录穿越漏洞；
  * 异常响应或调试接口中泄漏内部密钥、数据库物理路径及未脱敏的客户敏感凭证。
* **第二段位（跨租户越权、缓存投毒串味与并发穿盾，C1 进阶 + C2）**：
  * 批量操作、异步任务查询或子资源关联接口中的多维横向/纵向越权（IDOR）；
  * **缓存串味与权限滞后刺探**（红队脚本在租户 A 读取热点数据后，立即模拟管理员收回权限或切换租户 B 发起探测，检验选手新增的缓存是否造成跨租户信息泄露）；
  * **高并发条件竞争穿盾（TOCTOU）**：红队启动 30 路并发线程同时抢扣仅剩 1 次的稀缺安全配额或同时提交一次性核销令牌，检验是否能被并发击穿；
  * **签名伪造与时间窗重放攻击**：检验 Webhook/跨服务调用的常量时间签名比对（防时序侧信道）、时间戳过期拦截与随机流水号（Nonce）防重放机制。
* **第三段位（不对称资源耗尽 / 应用层拒绝服务攻击，C3 核心）**：
  * 红队脚本向检索与规则解析接口投递体积完全合法（小于 4KB），但经过精心构造的**三大算法复杂度炸弹**：
    1. **灾难性正则回溯炸弹（ReDoS）**：针对邮箱、URL 或自定义搜索语法匹配构造的恶意回溯字符串，未加固系统单次匹配即卡死 CPU 数秒；
    2. **深层嵌套与膨胀载荷炸弹**：深度嵌套或带大量重复键碰撞的畸形规则树/查询表达式；
    3. **慢查询放大攻击**：构造极端通配符或超大分页偏移请求企图拖垮数据库。
  * **实弹考核方式**：红队脚本一边并发投递上述恶意炸弹，一边模拟正常租户发送常规业务请求——不仅要求恶意请求被毫秒级安全拒绝/降级，还要求**同时进行的正常用户请求 P95 延迟完全不受拖累**！

## 四、全流程同仓运作机制（无外部主控台）

1. **选手开局（打点计时 + 创建带病系统沙盒）**
   * 被测模型进入仓库阅读 `AGENTS.md`，运行 `python tools/start_run.py --model <模型名>`。
   * 脚本打下起点时间戳 `t0`，锁定评测环境哈希承诺，并在 `runs/<模型名>/` 下初始化沙盒（含可正常运行的带病服务源码、基础业务功能冒烟测试、《性能剖析与安全加固阐述》模板）。
2. **选手收尾（冻结计时 + 提取脱敏代码差异补丁生成匿名包）**
   * 选手在沙盒内完成性能优化与安全加固、确保公开业务冒烟测试全绿、并填好阐述文档后，运行 `python src/scoring/judge_pack.py --model <模型名>`。
   * 脚本打下结束时间戳 `t1` 并固化代码 SHA-256；自动对比选手代码与初始沙盒代码，生成清晰可读的**全量改动差异补丁（`code_changes.diff`）**與改动统计，连同脱敏后的选手源码、阐述文档以及**《官方 5 级平庸参照补丁样本》**统一打入 `leaderboard/blind/<pack_id>/`，私有映射写入 `leaderboard/blind-maps/`。
   * **隔离红线**：匿名盲评包内**绝不放入模型名称，也绝不放入 A/B/C 的客观压测与红队攻防得分**。
3. **评委盲评（对照 5 级平庸样本审阅 Diff 补丁与架构思想，追加中心日志）**
   * 换评委智能体进场，只读 `leaderboard/blind/<pack_id>/` 路径。
   * 评委对照《5 级平庸参照补丁样本》，审阅选手的 `code_changes.diff`、源码与阐述文档，核查其性能优化是真正的算法/架构降维还是粗暴投机、安全加固是体系化收敛还是零碎打补丁、文档声明与代码实现是否诚实一致，通过 `judge_submit.py` 提交 D 层（30 分）评分至 `leaderboard/reviews.jsonl`。
4. **手动一键出榜（高压性能压测 + 红队实弹攻防定稿客观分 + 总分合成）**
   * 评委完成后，由维护者手动运行 `python leaderboard/finalize.py`。
   * **此时汇总脚本统一拉起 `score_run.py`**，依次对选手沙盒执行：① 全量业务结果零失真对账（B1）；② 大规模数据集与高并发读写混合性能压测（A）；③ 红队黑客三波实弹攻击与抗 DoS 轰炸（C）；计算客观分（70 分）并与中心日志的 D 层盲评分（30 分）合并生成 `leaderboard/scores.md`。
